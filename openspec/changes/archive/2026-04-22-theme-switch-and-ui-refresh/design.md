## Context

当前应用是 Vue3 + Electron 的单页工具，主题色和主要组件样式直接写在 `App.vue` 与 `style.css` 中，缺少可扩展的主题抽象层。页面目前以紫黑渐变和高饱和强调为主，整体视觉在“品牌辨识”和“专业工具感”上存在提升空间。

本次改造需要在不影响截屏、录屏与保存等核心流程的前提下，新增主题切换能力并重构视觉体系。约束包括：不引入新 UI 框架、不改动 Electron 主进程逻辑、尽量复用现有 DOM 结构以降低回归风险。

## Goals / Non-Goals

**Goals:**
- 支持 `light`、`dark`、`system` 三种主题模式，并在应用启动时正确恢复用户偏好。
- 建立语义化 CSS 变量体系，将关键组件样式迁移到 token 驱动。
- 将主界面改造为中性、克制、低饱和的工具型风格，避免紫黑“AI 模板感”。
- 保持现有功能行为与交互路径不变（仅改主题与视觉表达）。

**Non-Goals:**
- 不重构业务逻辑（屏幕源获取、录制、转码、保存流程）。
- 不新增第三方主题管理库或设计系统框架。
- 不进行跨页面改造（当前仅覆盖主界面）。

## Decisions

- 决策 1：主题状态以 `themePreference`（`light|dark|system`）保存，运行时解析为 `resolvedTheme`（`light|dark`）。
  - 方案 A（采用）：在 `App.vue` 内集中管理主题状态，初始化时读取 `localStorage`，并监听系统主题变化。
  - 方案 B（未采用）：新增独立状态管理库。  
  - 理由：当前应用规模较小，局部状态管理更轻量，且无需引入额外依赖。

- 决策 2：通过 `document.documentElement` 设置 `data-theme`，由全局 CSS 变量驱动主题切换。
  - 方案 A（采用）：`[data-theme="light"]` / `[data-theme="dark"]` 定义变量，组件只消费语义 token。
  - 方案 B（未采用）：在组件 class 上分别维护 light/dark 样式分支。  
  - 理由：变量方案可维护性更好，后续扩展主题成本低。

- 决策 3：保留现有结构，优先重构“高感知”视觉层（背景、面板、按钮、输入框、toast、滚动条）。
  - 方案 A（采用）：在不改动主要模板结构下替换视觉语言。
  - 方案 B（未采用）：大规模重排布局。  
  - 理由：当前用户诉求聚焦主题与风格，最小结构改动更稳妥。

- 决策 4：视觉方向采用“中性深浅对照 + 单一冷色强调”的工具化体系。
  - 方案 A（采用）：降低渐变使用频次，主背景改为实体色与轻微层次，强调色仅用于可交互焦点。
  - 方案 B（未采用）：继续强化多色渐变。  
  - 理由：更符合“去 AI 味、专业工具”目标，并提升长时间使用舒适度。

## Risks / Trade-offs

- [风险] 样式变量替换范围大，可能出现局部颜色遗漏 → [缓解] 建立 token 清单并按模块逐段替换与人工巡检。
- [风险] 系统主题监听在部分环境不触发 → [缓解] `system` 模式下提供手动切换兜底，并在初始化时强制计算一次。
- [风险] 深色模式对比度不足影响可读性 → [缓解] 对按钮、文本、边框按 WCAG 思路进行最小对比度校验。
- [权衡] 维持现有布局可降低风险，但视觉创新空间受限 → [收益] 交付更快、回归成本更低。

## Migration Plan

1. 先引入主题状态、偏好存储与 `data-theme` 应用逻辑，确保功能可切换。
2. 建立并落地基础 token（页面背景、文本、边框、面板、强调、状态）。
3. 分模块替换样式（header → panel → form/control → button/toast/scrollbar）。
4. 在 light/dark 下分别走通截屏、录屏、保存、复制关键路径。
5. 如出现显示异常，可临时回滚到上一版 `style.css`，保留主题逻辑后分步再替换。
